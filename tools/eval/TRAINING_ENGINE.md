# Training Engine offline evaluation

All inputs are synthetic. No model calls, network medical research, production data, or user health records are used.

Run after the catalog and engine data have been compiled:

```powershell
$env:TEMP=(Resolve-Path .cache/tmp).Path
$env:TMP=$env:TEMP
npx.cmd vitest run tests/training-engine
```

The suite samples 2,000 profiles using fast-check seed `20261015`. It covers six goals, two levels, one to six days, 10–90 minutes, five equipment scenarios, four populations, caution combinations, quiet/no-jump constraints, and explicit inability preferences. Every profile supplies a birth year/month, reference date, seven PAR-Q answers, symptom/condition state, and screening date. Population-specific confirmations are explicit.

The diagnostic report is written to `.cache/training-engine/report.json`. Categories are disjoint:

- `qualityPass`: explicit ready status, no blocked gates or hard validation/invariant errors, with every warning retained. Valid restricted intensity may be honored by a ready plan.
- `healthBlocked`: a health screening/population gate blocks generation; templates must be empty. These are never counted as quality passes.
- `limitedAllowed` / `unavailableAllowed`: an explicit status, complete issue list and registered status notice, plus independent proof of the source constraint or absence of safe candidates. Neither category is a quality pass.
- `algorithmFailure`: generation failure, missing status, hidden issues, or any claimed source limitation that the independent checker cannot prove.
- `throws`: generation/validation throws an exception.

The strict test fails for any algorithm failure, throw, independent hard invariant violation, or nondeterministic output. Source-limited cases are accepted only with the evidence above and remain separately counted. No test is skipped or marked as an expected failure. Historical reports retain their original `limitedIssues` field; they predate the approved classification and are not silently reclassified.

Twenty named golden profiles have explicit reviewable inputs in `training-engine-golden-inputs.json` and full output snapshots under `tests/training-engine/__snapshots__`. Snapshots show changes; separate schema, hardware, restriction, health-gate, and regression assertions check behavior. Update snapshots only after reviewing the corresponding behavior change.

Backend fixtures assemble typed intentions locally and check that missing screening and symptoms produce no actionable attachment. A fetch spy verifies that the rejected local path makes no outbound call. This is offline evidence, not a live model or preview-site test.

Recorded durations are Node CPU proxies. They do not establish a P95 on a mid-range mobile device. Real-device performance, preview-browser checks, and real-model evaluation remain separate. The requested ¥5 model budget has not been used.
